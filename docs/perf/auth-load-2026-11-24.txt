认证流程并发压测结果（2026-11-24）
=====================================

环境
----
云服务器：阿里云 2 核 2G（容器内可见 1.6GB），Ubuntu 24.04，Docker Compose，自签 TLS
应用参数：-Xms256m -Xmx384m -XX:+UseSerialGC，Hikari 连接池默认 10
数据库：MySQL 8.4.13，innodb-buffer-pool-size=256M，max-connections=50
压测机：开发虚拟机 192.168.216.130，Docker 镜像 grafana/k6（--insecure-skip-tls-verify）
数据规模：100000 条假用户 + 1 个管理员；表 18.5MB 数据 + 7.5MB 索引（全部可进缓冲池）

加压方式
--------
ramping-arrival-rate，每档 30 秒，共 90 秒；MAX_VUS=80，每个 VU 独占 200 个账号。
登录的三档：0→20 / 20→50 / 50→100 rps
注册、重置、改密的三档：0→10 / 10→20 / 20→40 rps


一、登录 POST /api/v1/auth/login
--------------------------------
tier1  0→20 rps   avg 171ms   p95 288ms
tier2 20→50 rps   avg 2.66s   p95 5.06s
tier3 50→100 rps  avg 3.41s   p95 5.30s

1694 次请求，实际吞吐 18.3 req/s，失败 10 次（0.59%），dropped_iterations 1905
结论：约 20 rps 以内健康，进入 20→50 档立刻塌陷


二、注册 POST /api/v1/auth/register
-----------------------------------
tier1  0→10 rps  p95 159ms
tier2 10→20 rps  p95 184ms
tier3 20→40 rps  p95 3.63s

1336 次请求，实际吞吐 14.5 req/s，失败 0，dropped_iterations 163
结论：约 20 rps 以内健康，40 rps 档塌陷


三、忘记密码 POST /api/v1/auth/password/reset
--------------------------------------------
tier1  0→10 rps  p95 170ms
tier2 10→20 rps  p95 284ms
tier3 20→40 rps  p95 3.90s

1357 次请求，实际吞吐 14.7 req/s，失败 8 次（0.58%），dropped_iterations 142
结论：与注册接近，约 20 rps 以内健康


四、修改密码 PUT /api/v1/users/me/password
------------------------------------------
每次迭代先登录再改密，只统计改密请求（登录单列）

tier1  0→10 rps  avg 419ms   p95 987ms
tier2 10→20 rps  avg 3.46s   p95 5.89s
tier3 20→40 rps  avg 3.99s   p95 7.64s

730 次迭代（730 登录 + 694 改密），失败 81 次（5.68%：登录 4.93%、改密 6.48%）
dropped_iterations 769
结论：容量最低，10 rps 档 P95 已接近 1 秒，实际可用约 5–8 rps


容器 CPU 采样（登录场景运行期间，每 4 秒一次）
---------------------------------------------
app    ：16% → 68% → 95% → 140% → 182% → 稳定在 185–197%（2 核上限 200%）
mysql  ：全程 2–9%
app 内存：425MB → 454MB（Xmx 384m + 元空间/直接内存）

瓶颈定位
--------
1. 应用 CPU 先饱和：BCrypt 是纯 CPU 操作，登录 1 次校验、注册/重置 1 次校验 + 1 次编码、
   改密 1 次校验 + 1 次编码，2 核跑满后请求排队。
2. 连接池成为第二道墙：Hikari 只有 10 个连接，排队线程超过后 3 秒超时，返回 500。
   日志中 10 分钟内 100 条：
   HikariPool-1 - Connection is not available, request timed out after ~3005ms (total=10, active=10, waiting=25+)
   本次三类场景的全部失败都来自这一条，不是数据库慢。
3. MySQL 全程 CPU < 10%，10 万数据量没有构成任何瓶颈：登录/重置走 uk_email，主键更新。

结论
----
- 登录、注册、忘记密码：2 核机器稳定容量约 20 rps（P95 < 300ms），40 rps 起 P95 到秒级
- 修改密码：稳定容量约 5–8 rps（一次迭代两次 BCrypt）
- 提升顺序（本轮不改，留作下一轮）：调大 Hikari 池 → 提高 BCrypt 并发效率（降低 cost 或加机器）
  → 再谈数据库与缓存

五、连接池调整后复测（同日 17:50）
----------------------------------
改动：hikari.maximum-pool-size 10 → 20，minimum-idle 2 → 5（可用 DB_POOL_SIZE / DB_POOL_MIN_IDLE 覆盖）
部署：预构建 jar + docker compose prebuilt 流程，旧 jar 保留为 app.jar.bak.7463017

登录场景（同一脚本、同一 10 万数据）：

              调整前            调整后
tier1 P95     288ms             254ms
tier2 P95     5.06s             5.17s
tier3 P95     5.30s             5.06s
吞吐          18.3 req/s        18.6 req/s
失败          10 次（Hikari）    0
app CPU       185–197%          175–195%
mysql CPU     2–9%              1–10%

结论：连接池 10 → 20 消除了 500，把失败变成慢成功；吞吐与 P95 基本不变。
瓶颈仍是应用 CPU：2 核跑满后请求只能排队，加连接池不增加算力。
下一步若要提吞吐，只能加机器/加实例，或换更轻的哈希（注意：BCrypt 校验成本由已存哈希的
cost 决定，降低编码强度只影响新密码，对存量用户无效）。
